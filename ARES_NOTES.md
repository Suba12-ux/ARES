# ARES --- уточнения, ограничения и инструкции для ИИ-модели

Этот файл предназначен для передачи GitHub Copilot и другим ИИ-моделям
вместе с репозиторием ARES. Он фиксирует контекст проекта, чтобы модель
не придумывала другую архитектуру и не делала лишнюю работу.

## 1. Контекст проекта

-   Название проекта: **ARES**. Не использовать название Jarvis.
-   Назначение: персональный голосовой ИИ-ассистент.
-   Основной сервер: уже имеющийся удалённый сервер под Ubuntu, доступен
    по IP `109.172.7.1`; домен пока не назначен, HTTPS отложен.
-   Локального сервера у пользователя нет.
-   Пользователь разрабатывает в Visual Studio Code с GitHub Copilot.
- Репозиторий уже подключён к GitHub: `Suba12-ux/ARES`, remote `origin`.
- Разработка ведётся в ветке `develop`; production обновляется после
  push в `main`.
-   `git push` пользователь выполняет самостоятельно.
-   Контейнеризация через Docker Compose --- обязательная часть
    архитектуры с самого начала.
-   Docker Hub не является обязательным и не планируется как базовое
    решение.
-   Предпочтительное хранилище образов --- GitHub Container Registry
    (GHCR).
-   CI/CD автоматизирует проверки, публикацию образа в GHCR и
    обновление production после успешного push в `main`.

## 2. Что означает «автоматизация», а что остаётся ручным

Ручные действия пользователя:

- редактирование и проверка кода;
- принятие изменений Copilot;
- выполнение `git push`;
- добавление необходимых секретов через безопасные настройки позже.

Автоматические действия после push:

- запуск CI и тестов на `develop` и `main`;
- сборка и публикация Docker-образа в GHCR;
- деплой на Ubuntu по SSH только после успешного push в `main` и
  прохождения всех обязательных проверок.

Не создавать отдельного агента, который самостоятельно коммитит или
пушит код, если пользователь явно этого не попросил.

## 3. Принципы архитектуры

1.  Сначала простой монолитный FastAPI backend, а не микросервисы.
2.  Docker Compose используется для локального тестирования и
    production-развёртывания, насколько это практически возможно.
3.  Внешняя LLM вызывается через API. Не предполагать наличие GPU или
    локальной большой модели.
4.  Поставщики LLM, STT и TTS должны быть заменяемыми через отдельные
    интерфейсы/адаптеры, но не создавать сложную абстракцию до появления
    второго реального провайдера.
5.  Не считать, что STT/TTS обязательно должны работать именно в
    контейнере: выбор зависит от задержки, цены, качества русского
    языка, приватности и доступности API.
6.  Не добавлять PostgreSQL, Redis, брокер сообщений, Kubernetes или
    другие сервисы без конкретной потребности. Для первого прототипа
    допустимо начать с минимального набора и добавить БД, когда появится
    реальное состояние, которое нужно сохранять.
7.  Если используется SQLAlchemy, миграции выполнять через Alembic. Для
    production-изменений схемы применять безопасные поэтапные миграции.
8.  Конфигурация --- через переменные окружения и типизированные
    настройки.
9.  Секреты не должны попадать в Git, Docker image, frontend bundle или
    логи.

## 4. Ограничения первого MVP

Первая версия должна обеспечить только базовый голосовой диалог: -
получить аудио; - распознать речь; - отправить текст в LLM; - получить
ответ; - озвучить ответ.

Пока не реализовывать: - постоянное прослушивание микрофона и wake
word; - произвольное управление ОС; - выполнение shell-команд по просьбе
модели; - автоматическое редактирование репозитория; - сложную агентную
систему с множеством инструментов; - векторную базу и сложную
RAG-систему; - мобильное приложение; - распределённую архитектуру.

Эти функции обсуждаются отдельно после рабочего MVP.

## 5. Требования к CI/CD

-   Пользователь отправляет изменения вручную.
-   Workflow запускается на push в согласованную ветку (например,
    `develop` и `main`) и/или через ручной запуск. Production-деплой
    выполняется только после push в `main`.
-   Сначала выполняются тесты и проверки.
-   Сборка/публикация образа выполняется только после успешных проверок.
-   Production-деплой запускается только после успешной публикации
    образа.
-   Использовать тег образа по commit SHA; не полагаться только на
    `latest`.
-   Не помещать SSH-ключ, пароли, API-ключи или содержимое `.env` в
    репозиторий.
-   Использовать минимальные permissions для `GITHUB_TOKEN`.
-   SSH-деплой должен использовать проверку host key, а не отключать её
    без причины.
-   До настройки CI/CD напомнить пользователю добавить необходимые
    GitHub Actions Secrets/Variables и подготовить серверные секреты.
-   После деплоя выполнять health check.
-   Не выполнять миграции БД автоматически без явно определённой
    безопасной процедуры и резервного плана.
-   Не удалять volumes при обычном обновлении контейнеров.
-   Продумать откат на предыдущий image tag.

## 6. Требования к Docker

-   Использовать Dockerfile с воспроизводимой установкой зависимостей.
-   По возможности использовать multi-stage build, если это
    действительно упрощает/уменьшает итоговый образ.
-   Приложение запускать от непривилегированного пользователя.
-   Не использовать `privileged: true` без веской причины.
-   Добавить `.dockerignore`.
-   Не копировать `.env` в image.
-   Данные БД и необходимые пользовательские данные хранить в volumes
    или внешнем постоянном хранилище.
-   Не публиковать порт БД в интернет.
-   Настроить health check и корректную обработку SIGTERM.

## 7. Безопасность будущих инструментов ARES

Когда появится управление компьютером: - модель не должна получать
неограниченный доступ к shell; - инструменты должны иметь явные схемы
аргументов и валидацию; - опасные операции (удаление, перезапись,
отправка данных наружу, выполнение команд) требуют подтверждения; -
ограничить доступ к каталогам и командам allowlist-подходом; -
логировать действия без секретов; - предусмотреть возможность отмены и
тайм-ауты.

## 8. Как ИИ-модели должны работать с репозиторием

Перед изменениями: 1. Прочитать `ARES_START_PLAN.md` и этот файл. 2.
Изучить фактическую структуру и текущий код репозитория. 3. Сопоставить
задачу с текущим этапом плана. 4. Кратко описать предлагаемые изменения
и список файлов. 5. Не переписывать существующий код без необходимости.

Во время изменений: - работать небольшими, логически завершёнными
шагами; - сохранять совместимость с уже принятыми решениями; - не
добавлять неоговорённые функции; - не генерировать фиктивные секреты,
домены, IP-адреса или значения конфигурации; - не предполагать
характеристики сервера, которых нет в документации; - не менять
технологический стек без объяснения и согласования.

После изменений: - показать, что изменено; - указать команды запуска и
проверки; - добавить/обновить тесты; - отметить, что не удалось
проверить; - обновить план или этот файл, если решение изменилось.

Если данных недостаточно, задать один конкретный вопрос вместо того,
чтобы угадывать.

## 9. Параметры, которые нужно заполнить

Не выдумывать значения. Заполнить, когда информация будет известна.

  Параметр             Значение
  -------------------- ----------------------------------------------------------
  Ubuntu version       Сервер имеется; версия не указана
  CPU architecture     Не указана
  CPU / RAM / disk     Не указаны
  SSH user             Не указан; не хранить пароль/приватный ключ в этом файле
  Server domain / IP   `109.172.7.1`; домен не назначен, HTTPS отложен
  GitHub repository    `Suba12-ux/ARES`, remote `origin`
  Development branch   `develop`
  Production branch    `main`; production после push в эту ветку
  LLM provider         DeepSeek; API-ключ добавит пользователь позже
  STT provider         Пока не выбрано
  TTS provider         Пока не выбрано
  Database for MVP     Решить по фактическим требованиям
  Public client type   Браузер / desktop-клиент --- выбрать отдельно

## 10. Приоритет текущей работы

Текущий приоритет --- получить надёжный, понятный и развёртываемый
голосовой MVP. Минимальный FastAPI-каркас уже запущен через Docker
Compose на сервере `109.172.7.1`. Домен не назначен, HTTPS пока отложен.

Workflow CI/CD реализован: он запускает проверки на `develop`/`main`,
публикует SHA-тегированный образ в GHCR и деплоит production через SSH
после успешного push в `main`. Для скачивания образа сервером пакет GHCR
должен быть публичным; используются только GitHub Environment
`production` Secrets/Variables для SSH. Порядок первой публикации и
перечень настроек описаны в `README.md`. После успешной проверки pipeline
выбрать STT/TTS и добавить голосовой цикл с LLM API, затем расширять
память и инструменты.

При конфликте между этим файлом и прямым новым указанием пользователя
следовать новому указанию, а затем обновить документацию.

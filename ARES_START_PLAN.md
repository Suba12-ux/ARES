# ARES --- план первого запуска (MVP)

**Статус:** стартовый план\
**Цель:** получить минимально работающего голосового ИИ-ассистента ARES,
развёрнутого на удалённом Ubuntu-сервере и запускаемого через Docker
Compose.

## 1. Исходные условия и принятые решения

-   Сервер уже арендован/имеется: удалённый Ubuntu, доступ по SSH.
-   Локального сервера нет; основная серверная часть ARES будет работать
    на удалённом сервере.
-   Разработку пользователь ведёт в Visual Studio Code с помощью GitHub
    Copilot.
-   Создание GitHub-репозитория, привязку GitHub и отправку (`git push`)
    пользователь выполняет самостоятельно.
-   Приложение с самого начала проектируется под Docker и Docker
    Compose.
-   Docker Hub не требуется. Для хранения образов можно использовать
    GitHub Container Registry (GHCR).
-   CI/CD нужен для автоматизации проверок, сборки образа и
    развёртывания после отправки изменений в выбранную ветку.
-   На первом этапе языковая модель вызывается через внешний API
    (например, OpenAI или DeepSeek); локальный запуск большой LLM не
    является требованием MVP.

## 2. Цель первого MVP

Первый MVP считается готовым, когда пользователь может открыть клиент
ARES на своём компьютере, произнести фразу, получить распознанный текст,
отправить его модели и услышать голосовой ответ.

В MVP пока не входят: - автономное управление компьютером; -
произвольное выполнение shell-команд; - сложная долговременная память; -
самостоятельное изменение исходного кода; - постоянное фоновое
прослушивание и wake word; - полноценный графический интерфейс.

Эти возможности добавляются отдельными этапами после устойчивой работы
базового сценария.

## 3. Предлагаемая архитектура

``` text
Компьютер пользователя
  └── Клиент ARES (браузер или лёгкое desktop/web-приложение)
       ├── микрофон
       ├── воспроизведение аудио
       └── HTTPS / WebSocket
              |
              v
Удалённый Ubuntu-сервер
  └── Docker Compose
       ├── reverse proxy (HTTPS)
       ├── FastAPI backend
       └── PostgreSQL (если подтверждена необходимость хранения данных
           уже в первом MVP; иначе начать проще и добавить позже)
              |
              v
Внешние API
  ├── LLM API
  ├── Speech-to-Text
  └── Text-to-Speech
```

Необязательно размещать распознавание речи и синтез речи на сервере: их
можно выполнять через API или на клиенте. Конкретный вариант выбирается
после проверки задержки, цены, качества русского языка и требований к
приватности.

## 4. Этапы реализации

### Этап 0. Уточнение окружения и ограничений

Сервер уже имеется по адресу `109.172.7.1`; домен не назначен, HTTPS
отложен. Репозиторий `Suba12-ux/ARES` подключён через remote `origin`.
Разработка ведётся в `develop`; production обновляется после push в
`main`. Версия Ubuntu, архитектура, CPU/RAM/диск и точные параметры SSH
остаются неуточнёнными и должны быть проверены на сервере.

**Результат:** известны адрес сервера и факт текущего деплоя; его
операционная система, ресурсы и SSH-параметры ещё нужно уточнить.

### Этап 1. Каркас репозитория

Создать минимальную структуру проекта, например:

``` text
ares/
├── backend/
│   ├── app/
│   │   └── main.py
│   ├── tests/
│   ├── Dockerfile
│   ├── requirements.txt
│   └── requirements-dev.txt
├── .github/                 # добавляется на этапе CI/CD
│   └── workflows/
│       ├── ci.yml
│       └── deploy.yml
├── compose.yaml
├── .gitignore
├── .env.example
└── README.md
```

Не создавать все каталоги и абстракции заранее без необходимости:
структура должна соответствовать реальному коду.

**Результат:** приложение FastAPI запускается локально и проходит
простой health check.

### Этап 2. Контейнеризация

-   Написать Dockerfile для backend.
-   Создать `compose.yaml`.
-   Настроить конфигурацию через переменные окружения.
-   Не помещать API-ключи и пароли в образ или Git.
-   Добавить health check.
-   Зафиксировать зависимости и использовать воспроизводимую сборку.
-   Проверить запуск и остановку через Docker Compose.

**Результат:** приложение стабильно запускается одной командой Compose.

### Этап 3. Первый деплой на Ubuntu

**Текущий статус:** минимальный backend уже развёрнут через Docker
Compose на сервере `109.172.7.1`. Настройка HTTPS отложена до появления
домена.

-   Проверить SSH-доступ.
-   Установить/проверить Docker Engine и Docker Compose plugin.
-   Подготовить каталог приложения на сервере.
-   Настроить firewall: наружу открывать только необходимые порты.
-   Настроить HTTPS через reverse proxy и сертификат.
-   Создать серверный `.env` с правами доступа, исключив его из Git.
-   Запустить контейнеры и проверить health endpoint.

**Результат:** пустой backend ARES доступен на сервере; HTTPS будет
добавлен отдельно после назначения домена.

### Этап 4. CI: проверки на GitHub Actions

**Текущий статус:** workflow `.github/workflows/ci-cd.yml` добавлен.
Для запуска publish/deploy пользователь должен заполнить GitHub
Environment `production`; затем необходимо проверить первый успешный
запуск Actions.

Пользователь самостоятельно делает `git push`. После push в рабочую
ветку GitHub Actions: - устанавливает зависимости; - запускает
линтер/форматтер, если они выбраны; - запускает тесты; - проверяет, что
Docker-образ собирается.

Проверки запускаются для `develop` и `main`; публикация образа и
production CD выполняются только для push в `main`.

**Результат:** ошибки обнаруживаются до деплоя.

### Этап 5. Публикация Docker-образа

Workflow публикует в GHCR образ с тегом commit SHA только после
успешных тестов и сборки на push в `main`. Для публикации используется
`GITHUB_TOKEN` с минимальным разрешением `packages: write`; подвижный
тег `latest` не используется. Образ собирается для Linux `amd64` и
`arm64`, чтобы не предполагать архитектуру Ubuntu-сервера.

**Результат:** после включения Actions и успешного push в `main` образ
ARES появляется в GHCR.

### Этап 6. CD: автоматическое обновление сервера

Workflow настроен на SSH-деплой только после успешной публикации образа.
Для первого реального запуска требуются заданные пользователем GitHub
Environment Secrets/Variables и проверенный SSH host key.

После успешных CI и публикации образа workflow подключается к серверу
по SSH с проверкой host key, передаёт `compose.yaml`, получает образ по
commit SHA, обновляет Compose и ожидает успешного Docker health check.
При ошибке workflow выводит логи и пытается восстановить предыдущий
образ.

Секреты SSH хранить только в GitHub Environment Secrets; серверный
`.env` сохраняется отдельно и не передаётся workflow. Пакет GHCR должен
быть публичным, чтобы сервер скачивал образ без отдельного токена.
Приватный SSH-ключ не хранить в репозитории.

**Результат:** пользователь по-прежнему вручную отправляет код в GitHub,
а сборка и доставка production-версии происходят автоматически.

### Этап 7. Голосовой диалог

Реализовать минимальный сквозной сценарий: 1. Клиент записывает короткую
аудиофразу. 2. Аудио передаётся backend или напрямую выбранному speech
API по безопасной схеме. 3. Speech-to-Text возвращает текст. 4. Backend
отправляет текст в LLM API вместе с системными инструкциями ARES. 5.
Ответ возвращается клиенту. 6. Text-to-Speech озвучивает ответ.

Добавить тайм-ауты, обработку ошибок API, ограничения
размера/длительности аудио и понятные сообщения пользователю.

**Результат:** первый голосовой разговор с ARES.

### Этап 8. Минимальный контекст и память

Сначала хранить только необходимое: - идентификатор сессии; - историю
последних сообщений; - настройки пользователя, если они нужны.

Определить срок хранения, способ удаления данных и лимит истории. Не
сохранять аудио постоянно без явной необходимости.

**Результат:** ARES учитывает недавний контекст диалога между запросами.

## 5. Безопасность и эксплуатация

Обязательные правила с первого деплоя: - секреты не коммитить; - `.env`
хранить только на сервере и локально, добавить в `.gitignore`; - не
публиковать PostgreSQL наружу без необходимости; - не запускать
контейнеры с `privileged: true` без обоснования; - по возможности
запускать приложение не от root; - ограничить SSH-доступ и использовать
ключи; - настроить firewall и HTTPS; - регулярно делать резервные копии
базы и проверять возможность восстановления; - ограничить размер аудио и
частоту запросов; - настроить firewall; HTTPS отложен до назначения
домена; - вести структурированные логи, не записывая в них секреты; -
для опасных инструментов в будущих версиях требовать
подтверждение пользователя.

## 6. Критерии готовности MVP

-   [ ] Репозиторий содержит исходный код и инструкции запуска.
-   [ ] Секреты отсутствуют в Git.
-   [ ] Backend запускается локально через Docker Compose.
-   [ ] Backend развёрнут на удалённом Ubuntu-сервере.
-   [ ] HTTPS и health check работают.
-   [ ] GitHub Actions запускает тесты и сборку на push.
-   [ ] Образ публикуется в GHCR.
-   [ ] Успешная сборка автоматически обновляет сервер.
-   [ ] Неуспешные тесты блокируют деплой.
-   [ ] Можно отправить голосовую фразу и получить озвученный ответ.
-   [ ] Ошибки внешних API обрабатываются без падения всего приложения.

## 7. Правило разработки с Copilot

GitHub Copilot используется как помощник по реализации, но не как
источник автоматически принимаемых архитектурных решений.

Для каждой задачи: 1. Давать Copilot одну ограниченную задачу и
ожидаемый результат. 2. Просить сначала перечислить план изменений и
затрагиваемые файлы. 3. Проверять diff перед принятием изменений. 4.
Запускать тесты и проверять Docker-сборку. 5. Не просить генерировать
весь проект одним большим запросом. 6. Не добавлять зависимости и
инфраструктурные компоненты без объяснения необходимости. 7. Обновлять
документацию при изменении архитектуры или команд запуска.
